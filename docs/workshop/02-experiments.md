# 02 — بروتوكول مقارنة الطرق الأربع

الحالة: بروتوكول مقترح، لا توجد نتائج تجارب مُنفّذة بعد.

## حاجات ثابتة قبل البداية

- نفس source commit ونفس `frontend/index.html` ونفس Express API وعينة بيانات اصطناعية.
- نفس coding agent، model identifier، effort إن توفر، وسياسة صلاحيات متكافئة.
- نفس versions المستهدفة، runtime، dependency policy، وحد وقت/تكلفة تقريبي متفق عليه.
- session وcheckout منفصلان لكل طريقة. لا تورث كود أو docs مولدة أو ذاكرة طريقة سابقة.
- نفس evaluator checklist وfixtures. قيّم سلوك الواجهة ضد API ثابت أو fixtures ثابتة بدل اختلاف إجابات LLM الحية.
- سجّل الوقت من بداية الفهم والتخطيط حتى أول نتيجة، وعدد التفاعلات والتدخلات ووقت الإصلاح منفصلة.

المقارنة بأربع runs تعلمية وليست برهانًا إحصائيًا. لو الوقت يسمح، كرر الطرق بترتيب مختلف، ولا تستنتج تفوقًا عامًا من run واحدة.

## التحكم في الـskills والـMCP

المقترح: التجارب 1–4 بنفس البيئة الأساسية دون skills اختيارية تفرض التخطيط تلقائيًا؛ استخدم Superpowers وباقي الأدوات في تجربة خامسة محسّنة منفصلة. تعليمات host أو الشركة الأساسية لا تُتجاوز.

لو البيئة تفرض Superpowers أو hooks أو AGENTS عالميًا، سجّل ذلك كعامل مؤثر. لا تسمِّ التجربة «Basic خالصة» إذا كان agent يدخل discovery/planning تلقائيًا. استخدم profile/session نظيفة إذا كانت الأداة تدعم ذلك، أو اذكر حدود المقارنة بوضوح.

بديل مقبول: تفعيل نفس domain skills ونفس MCP في الأربع runs، مع تسجيل ذلك. لكن تغيير prompt والـmodel والـskills معًا لا يسمح بعزل أثر الـprompt. وتفعيل Superpowers workflow في Basic قد يمنع الوصول لمعنى Basic المقصود أصلًا.

اختبارات التقييم تبقى ثابتة خارج workspaces التجارب. النسخة Basic لا تقرأ spec مفصلة مخفية في AGENTS أو docs، وإلا اتغيرت التجربة. قواعد سلامة الشركة تبقى مشتركة في كل الحالات.

## التجارب

| Run | المدخل | الناتج اللي نراقبه |
| --- | --- | --- |
| 01 Basic | التطبيق الأصلي + prompt قصير | الافتراضات، omissions، أول ناتج |
| 02 Detailed | نفس الأصل + متطلبات وظيفية وتقنية واضحة | أثر وضوح المتطلبات |
| 03 Master | نفس الأصل + مراحل discovery/BRD/architecture/plan/implementation/validation | أثر workflow كامل |
| 04 Spec Driven | نفس الأصل + spec بإصدارات وAC IDs وعقود ثم plan/tasks | التتبع والالتزام والقدرة على تغيير محدد |
| 05 Enhanced اختياري | أصل ثابت + spec driven + toolchain المختار | أفضل نسخة عملية؛ لا تنسب فرقها للـprompt وحده |

## خطوات كل run

1. أنشئ checkout مستقلًا من baseline واعرف الـHEAD. عند التنفيذ استخدم worktree skill أو آلية العزل المعتمدة.
2. سجّل الإعدادات والـskills/hooks النشطة في `docs/workshop/runs/0N/manifest.md` داخل مساحة تسجيل منفصلة عن المدخلات عند الحاجة.
3. أرسل prompt الطريقة فقط. كل follow-up وإجابة discovery تُسجّل؛ لا تمنح طريقة متطلبات إضافية بالخطأ دون توثيق.
4. اسمح للـagent باختبار وإصلاح عمله أثناء workflow، وسجّل ذلك. لا تعمل أنت تصحيحًا يدويًا قبل لقطة التقييم الأولى.
5. احفظ الناتج الأول قبل التعديلات البشرية في commit أو snapshot؛ لا تحذف الفشل.
6. شغّل checklist موحدة، وسجّل commands وexit codes والملاحظات ولقطات آمنة.
7. قيّم ودوّن الأسباب. بعدها ابدأ مرحلة الإصلاح وسجّل من أصلح ماذا ولماذا.
8. نفّذ change challenge واحدة ثابتة، مثل تغيير صياغة خطأ مع اختبار، وقارن تكلفة فهم وتعديل الكود.

## Checklist مشتركة

| ID | السيناريو | النتيجة المطلوبة |
| --- | --- | --- |
| EVAL-01 | تثبيت من lockfile ثم build | ينجح أو يُسجّل سبب الفشل الفعلي |
| EVAL-02 | login ثم session منتهية | تدفق متوافق مع الأصل ورسالة واضحة عند 401 |
| EVAL-03 | إرسال سؤال | نفس API payload وheaders؛ لا ظهور لسر provider في المتصفح |
| EVAL-04 | stream مجزأ على network chunks | النص والمصادر يظهران بدون فقد أو تكرار |
| EVAL-05 | provider error أو انقطاع stream | الخروج من loading وإتاحة محاولة واضحة |
| EVAL-06 | admin upload وagent upload | الواجهة متوافقة والصلاحية الحقيقية مفروضة بالـAPI |
| EVAL-07 | citations وواجهة ضيقة وkeyboard | مصادر مقروءة، لا overflow، وfocus مفهوم |
| EVAL-08 | فهم الكود وتغييره | يحدد المطور مكان state/API/stream ويعدل السلوك المحدد |

لا تعاقب كل runs على نقص معروف في الأصل مثل history الفارغ كأنه regression جديد. سجّل inherited gaps منفصلة عن regressions والمتطلبات الجديدة. Backend ثابت يعني اختبارات صلاحياته تثبت baseline؛ تقييم الواجهة يركز أيضًا على التعامل الصحيح مع ردوده.

## Rubric مقترحة ثابتة قبل رؤية النتائج

| البعد | الوزن | الدليل |
| --- | --- | --- |
| Accuracy | 30% | AC/checklist ناجحة من الإجمالي |
| Code quality | 15% | مثال واضح على typing والتكرار والمسؤوليات |
| Architecture | 15% | فصل UI/state/API ووضوح اعتماد المكونات |
| Maintainability | 15% | نتيجة change challenge وشرح مطور آخر |
| Scalability | 5% | تحليل حدود واقعي؛ لا نقاط لمجرد إضافة libraries |
| Assumptions | 10% | الافتراضات غير المطلوبة وتأثيرها |
| Effort | 10% | وقت كامل وتفاعلات وتدخلات وتكلفة إن متاحة |

لكل بعد درجة 0–5: صفر = لا دليل/تعطل كامل؛ 3 = يحقق الأساس مع نواقص محددة؛ 5 = يحقق المطلوب بدليل واضح. اكتب سبب الدرجة. للـAccuracy يمكن حسابها `5 × passed / total`، وللأبعاد الأخرى سجّل حكم المراجع. الإجمالي: `sum(weight × score / 5)` كنسبة من 100. الأوزان اختيار لهذا البروتوكول وليست من الشركة.

أنشئ `docs/workshop/comparison.md` عند وجود النتائج: جدول الطرق الأربع ودرجاتها وزمنها، روابط الأدلة، 3 ملاحظات، والقيود. لا تملأ أرقامًا تخمينية. اعرض أول ناتج وبعد الإصلاح في عمودين منفصلين.
