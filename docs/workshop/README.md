## القرار المقترح

ابدأ بتحويل واجهة الـCustomer Support الموجودة إلى Angular، مع تثبيت Express API أثناء المقارنة. بعد تسجيل النتائج، اعمل نسخة محسّنة باستخدام Superpowers + Impeccable + Angular skills + Angular CLI MCP. بعدها انقل الـbackend إلى NestJS + PostgreSQL كمرحلة مستقلة.

السبب: تغيير الواجهة والـbackend وقاعدة البيانات معًا يصعّب معرفة سبب الخطأ وسبب اختلاف النتائج. الـFull Stack مطلوب منك كاختيار شخصي، وهو بونص في تكليف الشركة.

دي توصية تنظيمية؛ لم يبدأ تحويل التطبيق أو تثبيت أي أدوات ضمن إعداد هذا الدليل.

## معنى Spec Driven عمليًا

```text
مشكلة واضحة → متطلبات قابلة للاختبار → عقد API وتصميم → خطة مهام
→ اختبار سلوك → تنفيذ صغير → تحقق ومراجعة → تحديث التوثيق
```

الـspec بتقول «إيه السلوك المطلوب وليه»، والخطة بتقول «هنحققه إزاي وفي أي ملفات». أي تغيير متفق عليه في السلوك يتسجّل في الـspec والاختبارات والخطة قبل استكمال التنفيذ.

مثال تتبّع:

```text
REQ-CHAT-01 → AC-CHAT-01 → TASK-CHAT-01 → chat-stream.spec.ts → evidence/run-01.md
```

اسم الاختبار هنا مثال مقترح، وليس ملفًا موجودًا أو نتيجة ناجحة.

## دور كل أداة

| الأداة | تستخدمها في إيه؟ | المخرج اللي تراجعه |
| --- | --- | --- |
| Superpowers | اكتشاف المتطلبات، التخطيط، التنفيذ التدريجي، debugging والتحقق | spec وخطة ومهام ودليل اختبارات |
| Impeccable | تخطيط UX، وضوح الواجهة، التصميم، الوصول، responsive والمراجعة البصرية | PRODUCT/DESIGN ولقطات وملاحظات قابلة للإصلاح |
| Angular skills | تطبيق conventions وواجهات Angular المناسبة للإصدار | components وservices وtests مفهومة |
| Angular CLI MCP | قراءة workspace، البحث في التوثيق، وتشغيل targets المتاحة | نتائج أدوات فعلية وأوامر build/test |
| NestJS skill | modules وDI وDTOs وguards والاختبارات | API وعزل مسؤوليات واختبارات صلاحيات |

الـskill تعليمات وخبرة إجرائية، والـMCP قناة لأدوات. وجودهم لا يثبت جودة النتيجة؛ الاختبارات والمراجعة هي الدليل.

## إزاي تطلع نتيجة أحسن؟

- ادّي الـAI سياق المهمة الحالية: هدف، spec، عقد، ملفات مرتبطة، قيود، ومعيار قبول.
- اطلب منه يفرّق بين حقيقة من المصدر، اقتراح هندسي، وافتراض يحتاج قرار.
- اشتغل feature واحدة من UI إلى API إلى DB؛ بلاش توليد النظام كله في رسالة واحدة.
- حدد المسموح تغييره، واعزل تحسينات التصميم عن تجربة الحفاظ على السلوك.
- اطلب اختبار failure وpermissions بجانب happy path. نجاح build وحده مش قبول وظيفي.
- اطلب اسم الأمر ونتيجته ورابط الدليل. لو أمر لم يُنفّذ، يتكتب «لم يُنفّذ».
- راجع الـdiff، وافهم تدفق البيانات، وعدّل جزءًا بنفسك قبل اعتبار المهمة متعلَّمة.
- خليك بسيط: modular monolith، ORM واحد، وstate محلي عند كفايته. أي إضافة كبيرة تحتاج سببًا مسجلًا.
- سجّل prompt والتدخل والقرار المفيد، بدل نسخ chat طويل لا يقدر الفريق يراجعه.
